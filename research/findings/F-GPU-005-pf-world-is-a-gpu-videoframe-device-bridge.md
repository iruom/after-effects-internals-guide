# PF GPU worlds bridge into shared VideoFrame and GPUFoundation device state

AE's public GPU-effect contract exposes `what_gpu` and `device_index`; the latter is explicitly intended for `PrSDKGPUDeviceSuite`. Installed `PF.dll` makes the internal bridge concrete.

High-signal exports include `CreateGPUEffectWorld(... shared_ptr<GF::Device> ...)`, `GPUFrameUpload(... MF::IVideoFrame, GF::Device ...)`, `GPUFrameToWorld(MF::IVideoFrame, PixelFormat)`, `IsEffectWorldGPUBased`, and PF-world/VideoFrame conversion functions.

This supports a layered model rather than a special isolated GPU pixel buffer:
`PF_LayerDef / PF_World <-> MF::IVideoFrame <-> GF::Device + framework/queue state`.
## Device and scheduling consequences
`PF.dll` also exposes `GetCurrentDevice`, `GetPrimaryMetalDevice`, `DeviceFrameworkToPFFramework`, renderer GUID get/set helpers, and GPU-support checks. `BEE.dll` exposes `GetNumThreadsAsPerAvailableGpuVram` in its render-task manager.

The strongest justified interpretation is that GPU backend/device choice is part of execution policy while PF worlds are host-managed views over a shared frame/device substrate. CPU callback return therefore cannot be equated with device completion; queue ownership and host-managed resource lifetime remain separate.

## Cache/identity caution
A renderer/device GUID is visible internally, but this does not prove that all GPU device state is directly mixed into every frame Render GUID. Treat execution identity, frame identity, and residency as separate until runtime correlation proves otherwise.
