# Render Graph Model

Trace vocabulary provides direct evidence for render-node concepts such as `RenderNode.RG_CacheNodeBase` and `RenderNode.RG_XformNode`.

This is the strongest reason to model AEIG's renderer as a graph-like runtime distinct from the project/property tree.

Key unknowns:
- graph construction lifetime
- node identity vs layer/effect identity
- transform fusion
- precomp boundary behavior
- ROI propagation
- cache-node placement
- temporal checkout edges

## Historical graph-rewrite evidence: concatenated rendering
Adobe patent US6084597 explicitly describes After Effects and a nested-composition optimization in which source layers are promoted into the root composition and rasterization/sampling is delayed until later rendering.

This is strong evidence that at least historically AE used composition-boundary rewriting rather than treating every nested composition as an unconditional framebuffer barrier.

A useful formal model is:
`nested node -> promote eligible child operations -> concatenate transforms -> delay sampling`

Eligibility cannot be purely structural. Masks, effects, blend operations, 3D renderer context, mattes and other non-commutative stages can become fusion barriers.

## Research questions
- Does modern Collapse Transformations still resemble promotion/concatenation at render-graph level?
- Where are `RG_XformNode` nodes placed before and after collapse?
- Are adjacent transforms fused or merely evaluated through a shared matrix chain?
- Which operations force materialization into an intermediate image?
- Do ROI and cache nodes move when a precomp barrier is removed?

## Design analysis
A cleaner modern architecture would encode graph-rewrite legality as operator traits: coordinate-space preserving, linear, rasterization barrier, temporal barrier, blend barrier, 3D-context barrier, etc. That makes optimization explicit and testable instead of attaching special rules to "precomp" as a UI concept.

## Distributed-SDK evidence added in 25.6 archaeology
CanvasSuite8 exposes a richer render topology than the project tree:
- ordered `AEGP_RenderLayerContextH` objects;
- a root/top-layer mapping that changes under collapsed geometrics;
- explicit 2D and 3D render bins;
- track-matte-specific context acquisition;
- per-layer texture/layer render paths;
- render receipts parameterized by effect-prefix count and geometry checking.

This makes the following provisional decomposition stronger:
`project model -> render-context expansion -> bin/graph construction -> pre-render/dependency work -> RG execution -> receipt/cache materialization`.

Local symbols independently expose `RG_Traverser::PreRenderGraph`, `RG_ExecuteGraph`, `RG_CompositeNode`, `RG_CacheNodeBase`, `RG_XformNode` and BEE render/task/GUID machinery.

## Important non-equivalences
Do not equate one project layer with one RG node, one render-layer context, one cache entry or one image buffer. Collapse, effect-prefix receipts, track mattes, adjustment layers, bounds expansion and 2D/3D partitioning all demonstrate reasons for one-to-many or many-to-one mappings.

The central reconstruction problem is now to identify the legal graph rewrite/materialization barriers and the state identity carried across each boundary.
## Binary module linkage strengthens the BEE → RG boundary
The installed AE 2025 `BEE.dll` has a direct PE dependency on `RG.dll`. Its import table includes `RG_Traverser::PreRenderGraph`, both `RG_ExecuteGraph` overloads, and multiple `RG_CacheNodeBase` methods including `CacheIsValid`, `IsValidCacheNodeData`, `ChildRequestHook`, `PreRender`, and `Render`.

This is stronger than a shared trace vocabulary: BEE code directly calls the RG module's graph/cache API surface.

In the same BEE binary, render-options/layer/item code exposes Render GUID formation and work-queue GUID acquisition. The current structural model can therefore place request identity/scheduling on the BEE side and graph/cache execution on the RG side, while leaving the exact object handoff and cache-key representation open.
